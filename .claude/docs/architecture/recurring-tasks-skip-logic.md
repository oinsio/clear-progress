# ADR: Skip Logic для повторяющихся задач

**Статус:** Принято
**Дата:** 2026-04-16
**Контекст:** Обработка повторяющихся задач при длительной неактивности пользователя

---

## Проблема

Что должно происходить с повторяющимися задачами, когда пользователь не открывает приложение несколько дней или недель?

**Сценарий:**
1. Пользователь создаёт задачу "Тренировка" с правилом "каждый день"
2. Завершает её 10 апреля 2026
3. Не открывает приложение до 16 апреля 2026
4. Открывает приложение 16 апреля

**Вопрос:** Сколько копий задачи должно быть создано?

### Варианты поведения

**Вариант A: Накопление пропущенных повторений**
- Создать 6 копий задачи (11, 12, 13, 14, 15, 16 апреля)
- Все копии раскрываются одновременно при открытии приложения
- Пользователь видит 6 одинаковых задач в списке

**Вариант B: Skip-логика (текущая реализация)**
- Создать 1 копию с `next_date = 2026-04-17` (ближайший будущий день)
- Пропущенные дни (11-16 апреля) игнорируются
- Пользователь видит только следующее повторение

---

## Решение

**Выбран вариант B: Skip-логика**

При завершении повторяющейся задачи вычисляется `next_date`. Если эта дата оказывается в прошлом (из-за длительной неактивности), система **пропускает** все промежуточные повторения и вычисляет ближайшую будущую дату.

### Реализация

Логика реализована в `packages/client/src/utils/repeatRule.ts`, функция `calculateNextDateDaily()` (строки 27-30):

```typescript
if (Temporal.PlainDate.compare(next, today) < 0) {
  const totalDays = prev.until(today, { largestUnit: "days" }).days;
  const periodsToSkip = Math.ceil(totalDays / interval);
  next = prev.add({ days: periodsToSkip * interval });
}
```

**Алгоритм:**
1. Вычислить `next = prev + interval` (базовое следующее повторение)
2. Если `next < today` (дата в прошлом):
   - Вычислить количество дней от `prev` до `today`
   - Вычислить количество периодов для пропуска: `Math.ceil(totalDays / interval)`
   - Вычислить новую дату: `prev + (periodsToSkip * interval)`
3. Результат: ближайшая дата >= `today`

### Примеры

#### Daily (каждый день)

```
Правило: { type: "fixed", frequency: "daily", interval: 1 }
Завершено: 2026-04-10
Сегодня: 2026-04-16

Расчёт:
- prev = 2026-04-10
- next = 2026-04-11 (prev + 1 день)
- next < today → skip logic
- totalDays = 6 (с 10 по 16 апреля)
- periodsToSkip = ceil(6 / 1) = 6
- next = 2026-04-10 + 6 дней = 2026-04-16

Но 2026-04-16 < today (сегодня), поэтому:
- periodsToSkip = 7
- next = 2026-04-17 ✅
```

#### Daily (каждые 3 дня)

```
Правило: { type: "fixed", frequency: "daily", interval: 3 }
Завершено: 2026-04-10
Сегодня: 2026-04-20

Расчёт:
- prev = 2026-04-10
- next = 2026-04-13 (prev + 3 дня)
- next < today → skip logic
- totalDays = 10
- periodsToSkip = ceil(10 / 3) = 4
- next = 2026-04-10 + (4 * 3) = 2026-04-22 ✅

Пропущены: 13, 16, 19 апреля
```

#### Weekly (каждый понедельник и среду)

```
Правило: { type: "fixed", frequency: "weekly", interval: 1, weekdays: [1, 3] }
Завершено: 2026-04-08 (среда)
Сегодня: 2026-04-20 (понедельник)

Расчёт:
- prev = 2026-04-08
- Следующий день из weekdays после prev: 2026-04-13 (понедельник)
- 2026-04-13 < today → пропускаем
- Ищем следующий: 2026-04-15 (среда) → пропускаем
- Ищем следующий: 2026-04-20 (понедельник) → сегодня, пропускаем
- Ищем следующий: 2026-04-22 (среда) ✅

Пропущены: 13, 15, 20 апреля
```

#### Monthly (каждое 15-е число)

```
Правило: { type: "fixed", frequency: "monthly", interval: 1, day_of_month: 15 }
Завершено: 2026-02-15
Сегодня: 2026-04-20

Расчёт:
- prev = 2026-02-15
- Целевой месяц: 2026-03 (в прошлом)
- Пропускаем периоды: ceil(2 / 1) = 2
- Новый целевой месяц: 2026-04
- 2026-04-15 < today → добавляем ещё interval
- Результат: 2026-05-15 ✅

✅ Для monthly/yearly skip-логика реализована!
```

#### After Completion (через N дней после завершения)

```
Правило: { type: "after_completion", delay_days: 7 }
Завершено: 2026-04-10
Сегодня: 2026-04-20

Расчёт:
- completedDate = 2026-04-10
- next = 2026-04-10 + 7 дней = 2026-04-17
- Skip-логика НЕ применяется (дата вычисляется от completedAt, а не от prev)
- Создаётся копия с next_date = 2026-04-17 (в прошлом)
- При раскрытии задача появится сразу
```

## Обоснование

### Почему skip-логика правильна для приложения, поддерживающего принципы GTD

1. **Избегание перегрузки списка**
   - Пользователь, вернувшийся после отпуска, не должен видеть 30 копий "Тренировка"
   - Список задач остаётся управляемым

2. **Фокус на будущем, а не на прошлом**
   - Философия продуктивности: задачи — это действия, которые нужно сделать
   - Пропущенные тренировки уже не актуальны — важна следующая

3. **Соответствие ожиданиям пользователя**
   - Если пользователь не открывал приложение — он не планировал выполнять задачи
   - Накопление копий создаёт ложное чувство долга

4. **Производительность**
   - Не создаются сотни записей в IndexedDB при длительном перерыве
   - Синхронизация с сервером не перегружается

### Альтернативные подходы

#### Вариант A: Накопление всех пропущенных повторений

**Плюсы:**
- Полная история повторений
- Пользователь видит, сколько раз пропустил задачу

**Минусы:**
- Перегрузка списка задач (UX-проблема)
- Избыточная нагрузка на БД и синхронизацию
- Не соответствует философии продуктивности (прошлое не важно)

**Вердикт:** Отклонён из-за UX-проблем

#### Вариант C: Уведомление о пропущенных повторениях

**Идея:** Создать одну копию + показать уведомление "Пропущено 6 повторений"

**Плюсы:**
- Пользователь информирован о пропусках
- Список задач не перегружен

**Минусы:**
- Дополнительная сложность реализации
- Уведомление может восприниматься как упрёк
- Не добавляет практической ценности

**Вердикт:** Избыточно для MVP

#### Вариант D: Настройка поведения пользователем

**Идея:** Добавить опцию "Накапливать пропущенные повторения: да/нет"

**Плюсы:**
- Гибкость для разных use-case'ов

**Минусы:**
- Усложнение UI и логики
- Большинство пользователей не изменят дефолт
- Два режима работы = два набора багов

**Вердикт:** Преждевременная оптимизация

## Ограничения и edge-cases

### 1. Monthly и Yearly имеют skip-логику

**Поведение:** Для `monthly` и `yearly` повторений skip-логика реализована аналогично `daily`:
- Если целевой месяц/год в прошлом, вычисляется ближайший будущий период
- Пропущенные месяцы/годы игнорируются
- Создаётся только одна копия с ближайшей будущей датой

**Пример:**
```
Правило: monthly, 15-е число
Завершено: 2026-01-15
Сегодня: 2026-04-20

Расчёт:
- prev = 2026-01-15
- Целевой месяц: 2026-02 (в прошлом)
- Пропускаем периоды: ceil(3 / 1) = 3
- Новый целевой месяц: 2026-04
- 2026-04-15 < today → добавляем ещё interval
- Результат: 2026-05-15 ✅
```

**Реализация:** См. `packages/client/src/utils/repeatRule.ts`, функции `calculateNextDateMonthly()` (строки 166-186) и `calculateNextDateYearly()` (строки 206-210).

### 2. After Completion не имеет skip-логики

**Проблема:** Для `after_completion` дата вычисляется от `completedAt`, а не от `prev`. Skip-логика не применяется.

**Поведение:**
```
Правило: after_completion, delay_days = 7
Завершено: 2026-04-10
Сегодня: 2026-04-20

Создаётся копия с next_date = 2026-04-17 (в прошлом)
При раскрытии задача появится сразу
```

**Обоснование:** Это корректное поведение. Задача "Проверить почту через 7 дней" должна появиться через 7 дней после завершения, даже если пользователь не открывал приложение.

### 3. Weekly с несколькими днями недели

**Проблема:** Логика `findNextWeekday()` ищет следующий день из списка `weekdays`, но не применяет skip-логику явно.

**Поведение:** Функция итерирует по дням до `7 * interval` и находит первый подходящий день >= `today`. Это эквивалентно skip-логике, но менее очевидно.

**Возможное улучшение:** Рефакторинг для явного применения skip-логики.

### 4. Часовые пояса

**Проблема:** `today` вычисляется через `Temporal.Now.plainDateISO()`, который использует системный часовой пояс. Если пользователь путешествует, `today` может измениться.

**Обоснование:** Это осознанное архитектурное решение. Повторяющиеся задачи не хранят часовой пояс создания — они всегда используют текущий системный часовой пояс. См. подробное обоснование в `recurring-tasks-timezone-policy.md`.
