# ADR: Политика часовых поясов для повторяющихся задач

**Статус:** Принято
**Дата:** 2026-04-16
**Контекст:** Обработка часовых поясов при вычислении дат повторяющихся задач

---

## Проблема

Должны ли повторяющиеся задачи хранить часовой пояс, в котором они были созданы?

**Сценарий из аудита (пункт 5 в `DATE_TIME_AUDIT_REPORT.md`):**

1. Пользователь создаёт задачу "Утренняя зарядка" с правилом "ежедневно" в Алматы (`Asia/Almaty`, UTC+5)
2. Завершает задачу 10 апреля 2026 в 08:00 по местному времени
3. Переезжает в Нью-Йорк (`America/New_York`, UTC-5)
4. Открывает приложение 16 апреля 2026

**Вопрос:** В каком часовом поясе должна вычисляться дата следующего повторения?

### Варианты поведения

**Вариант A: Хранить часовой пояс создания**
- `RepeatRule` содержит поле `timeZone: "Asia/Almaty"`
- При вычислении `next_date` используется сохранённый часовой пояс
- Задача "Утренняя зарядка" продолжает появляться в 08:00 по времени Алматы (что соответствует 18:00 предыдущего дня в Нью-Йорке)

**Вариант B: Использовать текущий часовой пояс (текущая реализация)**
- `RepeatRule` НЕ содержит поля `timeZone`
- При вычислении `next_date` используется `Temporal.Now.timeZoneId()` (текущий системный часовой пояс)
- Задача "Утренняя зарядка" появляется утром по времени Нью-Йорка

---

## Решение

**Выбран вариант B: Использовать текущий системный часовой пояс**

Повторяющиеся задачи **не хранят** часовой пояс создания. Все вычисления `next_date` и `appear_date` используют текущий часовой пояс системы (`Temporal.Now.timeZoneId()`).

### Реализация

**Модель данных:**
```typescript
// packages/client/src/types/common.ts
export interface RepeatRule {
  type: "fixed" | "after_completion";
  frequency?: "daily" | "weekly" | "monthly" | "yearly";
  interval?: number;
  // timeZone НЕ хранится намеренно
}
```

**Вычисление дат:**
```typescript
// packages/client/src/utils/repeatRule.ts
export function calculateNextDate(
  rule: RepeatRule,
  previousNextDate: string,
  completedAt?: string,
  clock: Clock = systemClock,
): string {
  const timeZone = clock.timeZoneId(); // Текущий часовой пояс
  // ...
}
```

**Ключевые точки:**
- `clock.timeZoneId()` всегда возвращает текущий системный часовой пояс
- При смене часового пояса устройства все последующие вычисления используют новый пояс
- Поле `timeZone` в `RepeatRule` намеренно отсутствует

---

## Обоснование

### Почему это правильно для приложения, поддерживающего принципы GTD

#### 1. Задачи vs Календарные события

**Задача** — это действие, привязанное к контексту и дню, но не к абсолютному моменту времени:
- "Утренняя зарядка" — это действие, которое нужно сделать утром текущего дня
- "Еженедельный обзор" — это действие в воскресенье, независимо от часового пояса
- "Оплатить счета" — это действие до конца месяца

**Календарное событие** — это встреча в конкретный момент времени UTC:
- "Звонок с коллегой в 10:00 UTC+5" должен остаться в 10:00 UTC+5, даже если пользователь в UTC-5
- "Вебинар в 15:00 по Москве" — фиксированный момент времени

**Clear Progress — это помощник для работы по методике GTD, а не календарь.** Задачи не привязаны к абсолютному времени, они привязаны ко дню и контексту.

#### 2. Естественное поведение для пользователя

Когда пользователь переезжает или путешествует, его распорядок дня адаптируется к новому часовому поясу:
- Утро наступает по местному времени
- Рабочий день начинается по местному времени
- Вечер заканчивается по местному времени

Повторяющиеся задачи должны следовать за этим естественным ритмом, а не оставаться привязанными к "домашнему" часовому поясу.

#### 3. Избегание путаницы

Если задача "Утренняя зарядка" появляется вечером (потому что привязана к часовому поясу создания), это создаёт когнитивный диссонанс:
- Пользователь видит задачу "Утренняя зарядка" в 18:00
- Задача помечена как "сегодня", но утро уже прошло
- Непонятно, нужно ли выполнять её сейчас или завтра утром

Использование текущего часового пояса устраняет эту путаницу.

#### 4. Простота модели данных

Отсутствие поля `timeZone` в `RepeatRule`:
- Упрощает модель данных
- Уменьшает размер записей в IndexedDB и Google Sheets
- Устраняет необходимость миграции данных при изменении логики
- Снижает вероятность багов (нет edge-case'ов с невалидными IANA-идентификаторами)

## Примеры сценариев

### Сценарий 1: Путешествие (краткосрочное)

**Контекст:**
- Пользователь живёт в Москве (`Europe/Moscow`, UTC+3)
- Создал задачу "Утренняя зарядка" (ежедневно)
- Улетел в командировку в Токио (`Asia/Tokyo`, UTC+9) на неделю

**Поведение:**
- В Москве: задача появляется утром по московскому времени
- В Токио: задача появляется утром по токийскому времени
- После возвращения в Москву: задача снова появляется утром по московскому времени

**Результат:** Задача всегда появляется утром по местному времени, что соответствует ожиданиям пользователя.

### Сценарий 2: Переезд (долгосрочное)

**Контекст:**
- Пользователь жил в Алматы (`Asia/Almaty`, UTC+5)
- Создал задачу "Еженедельный обзор" (каждое воскресенье)
- Переехал в Нью-Йорк (`America/New_York`, UTC-5)

**Поведение:**
- В Алматы: задача появлялась в воскресенье по времени Алматы
- В Нью-Йорке: задача появляется в воскресенье по времени Нью-Йорка

**Результат:** Задача остаётся в воскресенье, но адаптируется к новому часовому поясу.

### Сценарий 3: Контраст с календарём

**Контекст:**
- Пользователь в Москве (`Europe/Moscow`, UTC+3)
- Календарное событие: "Звонок с клиентом в Нью-Йорке в 10:00 по Нью-Йорку"
- Задача: "Подготовиться к звонку"

**Поведение:**
- Календарное событие: должно остаться в 10:00 UTC-5 (18:00 по Москве)
- Задача: появляется в день звонка по московскому времени

**Вывод:** Календарные события требуют фиксированного часового пояса, Задачи — нет.

### Сценарий 4: After Completion

**Контекст:**
- Пользователь в Лондоне (`Europe/London`, UTC+0)
- Задача "Проверить почту" с правилом `after_completion`, `delay_days = 3`
- Завершил задачу 10 апреля в 14:00
- Улетел в Сидней (`Australia/Sydney`, UTC+10) 11 апреля

**Поведение:**
- `completedAt` = `2026-04-10T14:00:00.000Z` (UTC)
- При вычислении `next_date` используется часовой пояс Сиднея
- `completedAt` конвертируется в дату по Сиднею: `2026-04-11` (уже следующий день из-за UTC+10)
- `next_date` = `2026-04-11` + 3 дня = `2026-04-14`

**Результат:** Дата следующего повторения вычисляется от даты завершения в текущем часовом поясе.

## Альтернативные подходы

### Вариант A: Хранить часовой пояс в RepeatRule

**Идея:** Добавить поле `timeZone: string` (IANA-идентификатор) в `RepeatRule` и использовать его при вычислении `next_date`.

**Плюсы:**
- Точность для пользователей, которые хотят сохранить привязку к "домашнему" часовому поясу
- Предсказуемость: задача всегда появляется в одно и то же время UTC

**Минусы:**
- Усложнение модели данных (дополнительное поле в каждой повторяющейся задаче)
- Не соответствует философии продуктивности (задачи привязаны ко дню, а не к моменту времени)
- Путаница для пользователя: задача "Утренняя зарядка" появляется вечером
- Edge-case'ы: невалидные IANA-идентификаторы, изменение правил DST, устаревшие идентификаторы
- Миграция данных: что делать с существующими задачами без `timeZone`?

**Вердикт:** Отклонён. Решает проблему меньшинства пользователей, создавая проблемы для большинства.

### Вариант B: Настройка поведения пользователем

**Идея:** Добавить глобальную настройку "Привязывать повторяющиеся задачи к часовому поясу создания: да/нет".

**Плюсы:**
- Гибкость для разных use-case'ов
- Пользователь сам выбирает поведение

**Минусы:**
- Усложнение UI (дополнительная настройка, которую нужно объяснить)
- Два режима работы = два набора багов и edge-case'ов
- Большинство пользователей не изменят дефолт
- Непонятно, какой дефолт выбрать (любой выбор будет неправильным для части пользователей)

**Вердикт:** Преждевременная оптимизация. Можно добавить в будущем, если появится реальный запрос.

### Вариант C: Гибридный подход

**Идея:** Использовать текущий часовой пояс для `daily`/`weekly`, но хранить часовой пояс для `monthly`/`yearly`.

**Обоснование:** Месячные/годовые задачи часто привязаны к конкретным датам (оплата счетов, годовщины), которые могут иметь юридическое значение.

**Плюсы:**
- Баланс между простотой и точностью

**Минусы:**
- Непоследовательность: разное поведение для разных типов повторений
- Усложнение логики и тестирования
- Всё ещё не решает проблему для `after_completion`

**Вердикт:** Отклонён. Непоследовательность хуже, чем единообразное поведение.

## Ограничения и edge-cases

### 1. Пользователи, часто путешествующие

**Проблема:** Для пользователей, которые часто меняют часовые пояса (цифровые кочевники, пилоты, моряки), текущее решение может быть неожиданным.

**Пример:**
- Пользователь создал задачу "Позвонить маме" (каждое воскресенье в 10:00)
- Путешествует по миру, меняя часовые пояса каждую неделю
- Задача появляется в воскресенье, но "10:00" по местному времени может быть неудобным временем для звонка в "домашний" часовой пояс

**Обоснование:** Это редкий use-case. Для таких пользователей:
- Можно создать отдельную задачу с конкретным временем в описании ("Позвонить маме в 10:00 по Москве")
- Можно использовать календарь вместо задачи
- В будущем можно добавить опциональную настройку (Вариант B)

### 2. Переход через полночь

**Проблема:** При завершении задачи в 23:50 по местному времени и смене часового пояса дата завершения может измениться.

**Пример:**
- Пользователь в Токио (UTC+9) завершает задачу 10 апреля в 23:50
- `completedAt` = `2026-04-10T14:50:00.000Z` (UTC)
- Переезжает в Лондон (UTC+0)
- При вычислении `next_date` дата завершения конвертируется в `2026-04-10` по Лондону (тот же день)
- Но если бы остался в Токио, дата была бы `2026-04-10` по Токио

**Обоснование:** Это корректное поведение. Дата завершения — это дата по текущему часовому поясу в момент вычисления. Альтернатива (хранить дату завершения в часовом поясе создания) создаёт больше проблем, чем решает.

### 3. DST (Daylight Saving Time)

**Проблема:** При переходе на летнее/зимнее время часовой пояс остаётся тем же (например, `Europe/Paris`), но смещение UTC меняется.

**Поведение:** Temporal API автоматически обрабатывает DST. Задачи продолжают появляться в тот же день, независимо от перехода на летнее время.

**Обоснование:** Это корректное поведение. Задачи привязаны ко дню, а не к моменту времени UTC.

### 4. Невалидные часовые пояса

**Проблема:** Что если `Temporal.Now.timeZoneId()` вернёт невалидный IANA-идентификатор?

**Обоснование:** Это невозможно. `Temporal.Now.timeZoneId()` всегда возвращает валидный IANA-идентификатор, определённый системой. Если система настроена неправильно, это проблема системы, а не приложения.
